# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A NixOS flake for two x86_64-linux machines: `unclebeam-pc` (AMD Ryzen 9 desktop + AMD RDNA GPU, gaming) and `unclebeam-thinkpad` (ThinkPad X1 Carbon Aura, Intel). Both run NixOS 26.05 + **niri** (26.04 straight from the 26.05 pin — the compositor no longer rides nixpkgs-unstable; that was a hyprland-era exception) with its **KDL config** (the compositor lineage is sway → hyprland → niri → hyprland again → niri again: niri won the second comparison too, and the hyprland re-trial ended 2026-08-17 with a full deletion — the hyprland Lua setup lives in git history on `main`). The repo is edited primarily **on the Linux machines themselves**; the Mac is used as a remote install trigger (nixos-anywhere) and can only `nix eval` for validation — it can never build or switch.

## Commands

```sh
# Validate a config after edits (works cross-platform, incl. this Mac —
# evaluation only, no build). This is the main "did I break it" check:
nix eval .#nixosConfigurations.unclebeam-pc.config.system.build.toplevel.drvPath
nix eval .#nixosConfigurations.unclebeam-thinkpad.config.system.build.toplevel.drvPath

# Sanity-check the compositor config after editing the KDL (on a machine):
niri validate

# Apply on a machine (hostname == flake attr, so no #name needed there):
sudo nixos-rebuild switch --flake .

# Smoke-test in a VM (Linux only):
nixos-rebuild build-vm --flake .#unclebeam-pc && ./result/bin/run-unclebeam-pc-vm

# Update pins (stays within the nixos-26.05 branch):
nix flake update
```

**⚠ Flakes only see git-tracked files.** After creating any new `.nix` file, `git add` it before evaluating/building — otherwise you get misleading "path does not exist" errors.

## Hard-won rules

These each caused a real failure at least once. Follow them literally.

- **A change is not "done" until it evals, is committed, AND is pushed — but a manual gate splits the work.** Half-committed or unvalidated work broke an install once — the machine pulled a state where only part of a change existed. So the work happens in two stages with the human's own rebuild in between. First: `nix eval` passes for BOTH hosts, then `git add .`, and **stop there — do not commit or push yet.** The human rebuilds and switches on their own machine first; only once they confirm it works do you commit, push, and print the commit sha. When wiring a new flake input, verify all three places it must appear: the input declared in `flake.nix`, its module wired into `mkHost`, and the import in the host that uses it.
- **Never invent hardware facts.** `hardware-configuration.nix` contents, `/dev/disk/by-id/` paths, filesystem UUIDs, monitor names — these only come from the target machine. If one is missing, stop and ask the human; leave a clearly marked placeholder rather than guessing. A plausible-looking made-up value is worse than a loud gap, because disko will happily format the wrong disk. The niri-flavored corollary: output names in `home/niri/hosts/*.kdl` are matched against the FULL "Make Model Serial" string from `niri msg outputs` with **no prefix matching** — a name even one character off silently never matches (the panel just auto-configs, no error), and hyprland's `desc:` strings are NOT reliable sources (verified difference: the Gigabyte M28U is "CO., LTD." in niri, "CO. LTD." in hyprland). Names must be verified verbatim on-machine.
- **Installs and reinstalls must pin an exact commit sha** — `github:unclebeam/nix-config/<sha>#<host>` — to bypass Nix's flake tarball caching (a branch ref can serve a cached tarball up to an hour stale, i.e. *not* the commit you just pushed). Branch refs are fine only for daily on-machine rebuilds with `--flake .`, where the repo is a local checkout and there's nothing to cache.
- **Know which PAM service a display manager actually traverses.** When SDDM was the greeter, its PAM service was generated with `useDefaultRules = false` — a bare `substack login` — so per-service toggles like `sddm.kwallet`/`sddm.fprintAuth` were silent no-ops (one sat in the old niri.nix for months doing nothing; the keyring unlock actually came from a module hooking `login`). The current greeter runs on **greetd**, whose PAM service is generated WITH default rules and does NOT substack `login`: toggles on `security.pam.services.greetd` genuinely work, and toggles on `login` no longer fire at graphical login. (The DMS lock screen authenticates against `/etc/pam.d/login`, so that service still matters.) Before setting any per-service PAM option, check how that service is generated.
- **Every session entry the greeter lists must actually boot — audit the session files a compositor package ships.** The hyprland package unconditionally shipped TWO session files, and the second (`hyprland-uwsm.desktop`, with no uwsm units behind it) killed logins in under a second (journal 2026-07-20: exit status 5 → session closed → bounced back to the greeter). The fix then was a link-farm force-filter on `services.displayManager.sessionPackages`; that filter is GONE now because the niri package ships exactly ONE `niri.desktop` (verified) — there is nothing to filter, and `programs.niri` never enables uwsm. If a compositor/session package ever changes or another appears, list its `share/wayland-sessions/` before trusting the greeter menu, and re-add a filter only if a broken entry shows up.

## Architecture

`flake.nix` defines a `mkHost` helper; each host is one `nixosConfigurations` entry whose modules are: the host dir, disko's NixOS module, and home-manager wired in as a NixOS module (`useGlobalPkgs`, so one `nixos-rebuild switch` builds system + user config together, and `allowUnfree` from core.nix applies to user packages too). The `nixpkgs-unstable` input feeds only fast-moving leaf apps (claude-code, lazygit, starship, brave, chrome, vscode, slack) — the compositor is NOT among them anymore.

Three layers, each with a strict role:

- **`hosts/<name>/`** — deliberately THIN: hostname, hardware quirks (GPU, microcode, zram), `stateVersion`, and which shared modules to import. Importing a module *is* enabling it (e.g. the thinkpad gets gaming.nix by uncommenting one import line). Each host also has:
  - `hardware-configuration.nix` — machine-generated by `nixos-generate-config`; its `fileSystems.*` entries were removed because disko generates them.
  - `disko.nix` — declarative disk layout (GPT → 512M vfat ESP → btrfs with `@`/`@home` subvolumes, zstd compression). Dual purpose: nixos-anywhere uses it to **wipe and format** the disk at install time, and at run time it generates the mount config. Target disks are pinned by stable `/dev/disk/by-id/nvme-<model>_<serial>` paths, never `/dev/nvme0n1`.
- **`modules/`** — shared NixOS (system-level) modules: `core.nix` (nix settings, systemd-boot, NetworkManager, the user, baseline packages), `nix-config.nix` (first-boot clone of the `~/nix-config` checkout — the target of every out-of-store symlink; no-op once it exists), `desktop.nix` (fonts + Wayland-wide env + fallback GTK portal), `niri.nix` (niri session + portal routing: KDE for dialogs — with `lib.mkForce`, because `programs.niri` hard-sets its portal keys as plain strings, unlike programs.hyprland which set none — and GNOME for capture, niri's ONLY screencast backend: niri implements `org.gnome.Mutter.ScreenCast`, a public D-Bus API with no compositor/portal version coupling, hence no unstable pin and no paired-bump rule; also `useNautilus = false` so Dolphin keeps FileChooser + FileManager1, `xwayland-satellite` on the system path for X11 clients, and `defaultSession`), `dms.nix` (THE DMS shell: flake NixOS module enable + dms.service + UI fonts + upower + the `input` group for its evdev keybind recorder), `dms-greeter.nix` (login greeter: DMS's greeter UI on greetd, `compositor.name = "niri"`, syncs the user's wallpaper/colors into /var/lib/dms-greeter), `kwallet.nix` (session keyring: ksecretd + pam_kwallet auto-unlock on `greetd`, plus the LIVE gnome-keyring off-switch and the mkForce Secret→kwallet portal route — programs.niri enables gnome-keyring by mkDefault and hard-sets Secret=gnome-keyring; user half in `home/kwallet.nix`), `dolphin.nix` (avahi, udisks2, ntfs/exfat — the system half of the file manager), `audio.nix`, `gaming.nix` (NB: HDR gaming is PARKED — niri 26.04 has no color management; the hyprland-era auto-HDR recipe lives in git history), `laptop.nix`.
- **`home/`** — shared home-manager (user-level) config, identical on both machines; entrypoint `home/default.nix` imports niri/dms/alacritty/fish.

**System vs. user split for the desktop**: `modules/niri.nix` enables niri at the system level (session .desktop file, portals, xwayland-satellite); the actual window-manager *configuration* lives in `home/niri.nix` plus the plain KDL file `home/niri/config.kdl` (**out-of-store** symlinked into the `~/nix-config` checkout — same rule and same hardcoded base path as the editor configs). niri **watches** its config and every include and live-reloads on save: edit → applied, no rebuild, no reload command (the hyprland era's `hyprctl reload` ritual is gone; `niri validate` checks syntax before a risky logout). Include gotchas that each bit us once: includes are POSITIONAL and merge LAST-WINS; relative include paths resolve against the file's real directory (`~/nix-config/home/niri/`, not `~/.config/niri/`), so every include uses a `~` path; and a missing non-`optional=true` include fails the WHOLE config, dropping niri to its built-in defaults. Per-machine display config — `output` blocks only — lives in **`home/niri/hosts/<hostname>.kdl`**, one tracked file per host, and `home/niri.nix` symlinks exactly one of them to `~/.config/niri/host.kdl` based on `osConfig.networking.hostName` (`osConfig` is the NixOS config, available in every home module because home-manager is wired in as a NixOS module). So `config.kdl` is host-agnostic — there is no `/etc/hostname` read and no host branch, and the other machine's outputs are never loaded. Tracking these is safe *because* Nix picks one, and it means a fresh install boots with the right layout instead of auto-config. The contents are still hardware facts: verified against `niri msg outputs` on the machine, never invented (see the hard-won rule — full-string matching, no prefixes). `home/niri.nix` `assert`s the host's file exists in the flake source, so a forgotten `git add` fails at eval instead of dangling into a broken session. There are NO workspace pins and NO undock hook anymore: niri's workspaces are dynamic and per-monitor, so undocking just migrates orphaned workspaces to the live output (the whole hyprland-era "solo login lands on workspace 9" bug class is structurally gone). One file is Nix-GENERATED: `~/.config/niri/nix.kdl` mirrors the cursor theme/size from `home.pointerCursor` (niri reads its cursor from config, not XCURSOR_* env). Keep additions on the right side of the line: config-less system packages go in core.nix, apps with per-user config go in home/.

**The shell is DMS (DankMaterialShell); apps are KDE; screen capture is the GNOME portal.** Since 2026-08 (replacing Noctalia — the shell lineage is waybar-stack → DMS → Noctalia → DMS again; this second DMS era pairs it with niri, DMS's original home-turf compositor), one shell (the `dank-material-shell` flake input, `/stable` branch = latest release) is the bar, launcher (spotlight), notification daemon, lock screen, idle policy, OSD, clipboard history, polkit agent (built in, always on), power menu, wallpaper, screenshot tool — and the same flake's `nixosModules.greeter` is the greetd greeter. **The flake input is mandatory: nixpkgs 26.05's `dms-shell` package is frozen at 1.4.6, too old** (and on upstream's master the greeter has moved to a separate `dank-greeter` repo — the first `nix flake update` that lands 1.6 needs a new input + option namespace, see flake.nix). DMS is a Go daemon that spawns quickshell; unlike the noctalia era there is NO binary cache, which is why this input DOES set `inputs.nixpkgs.follows` — quickshell comes prebuilt from cache.nixos.org and only the small Go daemon compiles per bump. Upstream ships a NixOS module AND home-manager modules — we use the **NixOS module only** (`modules/dms.nix`: enable + the one `dms.service` user unit scoped to niri-session.target + upower + UI fonts (inter/fira-code/material-symbols) + the `input` group; `modules/dms-greeter.nix`: greeter, which enables greetd itself; `home/dms.nix`: user-side glue ONLY — adw-gtk3 + the `~/.config/niri/dms` mkdir + the alacritty dank-theme.toml placeholder, it imports no DMS module). Never import the flake's homeModules (two service owners) — and **especially never `homeModules.niri`**: its includes-hack takes over `~/.config/niri/config.kdl`, which is our out-of-store symlink. Never spawn `dms run` from config.kdl — the shell must not run twice. Interaction is `dms ipc call <target> <fn>` (`dms ipc list` enumerates); **the keybinds are OURS**, in the tracked `home/niri/config.kdl` — DMS's `dms setup` fragments (`~/.config/niri/dms/binds.kdl`, layout.kdl, …) are deliberately unused, and `dms setup` itself is never run: the ONE fragment we consume is `dms/colors.kdl` (matugen-written on every wallpaper change), pulled in by config.kdl's trailing `include optional=true`. Configuration is GUI-OWNED by upstream design: the Settings GUI (SUPER+Shift+comma — SUPER+comma is niri's stock consume-window-into-column) persists everything in `~/.config/DankMaterialShell/settings.json`; there is no tracked-baseline layer (noctalia's config.toml had one — accepted regression, and don't reach for the home module's `settings` option to fake it, it makes the GUI fight Nix). Consequence: a fresh install boots to a working bar/launcher/keybinds with zero shell-side setup (modules/nix-config.nix clones the checkout, retrying every 15s until network/DNS works — login is only possible ≤15s after network comes up; the greeter lists exactly one session), but **idle/lock timeouts default to 0 = the machine never auto-locks until set in the GUI**. First-login steps per machine: pick a wallpaper (SUPER+Y) so matugen writes colors.kdl + the app themes, set the idle timeouts in Settings (lock 600s / screen-off 660s; thinkpad also the battery pair + lock-before-suspend), toggle "Apply GTK Themes" + "Apply Qt Themes" on once, verify the output names in host.kdl against `niri msg outputs`, and (thinkpad) `fprintd-enroll`. Doom Emacs keeps its own split (`home/emacs.nix`): the framework clone into `~/.config/emacs` is automatic (the `clone-doom-emacs` user oneshot, ConditionPathExists-guarded like the nix-config clone; retries next login if network wasn't up), while `doom install` — minutes of package building, upstream's interactive path — is a manual first-login step, followed by `systemctl --user restart emacs.service` so the daemon (which started bare) loads Doom. The KDE app layer stays: Dolphin + Ark + KIO, secrets in ksecretd (`modules/kwallet.nix` + `home/kwallet.nix`, auto-unlocked via pam_kwallet on `greetd` — which is why the greeter must stay password-only, see modules/fprintd.nix), dialogs/notifications/settings route to `xdg-desktop-portal-kde`. Do not re-add gnome-keyring — and note `programs.niri` tries to (mkDefault): kwallet.nix's `services.gnome.gnome-keyring.enable = false` is a LIVE override now, not hygiene. The exception: ScreenCast/Screenshot/RemoteDesktop route to **`xdg-desktop-portal-gnome`** (installed by programs.niri; niri implements org.gnome.Mutter.ScreenCast, its only capture path). Never route the capture family to `kde` — xdg-desktop-portal-kde's capture code is hard-wired to KWin's private `zkde_screencast` protocol and can never work here. GlobalShortcuts is deliberately unrouted (its xdph impl left with hyprland; nothing consumes it). One accepted regression: the xdph restore-token tuning is gone, so browser/vesktop re-shares open the picker each time. (Screenshots themselves don't go through the portal: the Print binds run the `screenshot-annotate` wrapper — `home/satty.nix` owns it and the annotator — which captures via `dms screenshot … --stdout` with file/clipboard/notify off and hands the image to satty; nothing lands anywhere until Enter commits inside satty.)

**Theming**: DMS owns color, via **matugen**. The shell derives a Material You palette from the wallpaper and (re)renders its template outputs on every wallpaper change: `~/.config/niri/dms/colors.kdl` (focus-ring/border/shadow/tab-indicator/recent-windows colors — pulled in by the LAST include in config.kdl, `optional=true` so it's simply absent before the first wallpaper; its bottom position is what lets the palette override the stock colors, since includes merge last-wins; NO reload hook — niri watches includes, and unlike noctalia's template DMS never edits config.kdl itself), `~/.config/alacritty/dank-theme.toml` (imported by alacritty.nix; seeded as an empty placeholder by home/dms.nix so the import never dangles), `~/.config/gtk-{3,4}.0/dank-colors.css` + adw-gtk3(-dark) via gsettings (behind the "Apply GTK Themes" toggle, default OFF — a first-login step), and `~/.local/share/color-schemes/DankMatugen.colors` (a KColorScheme merged into `~/.config/kdeglobals` for live KF6 recolor, behind "Apply Qt Themes"; `home/qt.nix` points qt6ct/qt5ct's `color_scheme_path` at it and sets `QT_QPA_PLATFORMTHEME=qt6ct` — Dolphin needs the KDE build, `kdePackages.qt6ct` — and its seed also repairs upstream qt.sh's literal-`\n` create-corruption). All template outputs are written imperatively by DMS — configs reference them via includes/imports, never via a store symlink (that would block the writes; it's also why home/niri.nix links individual files, keeping `~/.config/niri` a writable dir, and why qt6ct.conf/dank-theme.toml stay plain files). They're machine-local and untracked (each machine's wallpaper differs). There is no repo palette; don't hardcode theme colors in app configs — let DMS's theming reach them, or leave the app at its defaults (satty, mangohud).

**Invariants to preserve**:
- `nixosConfigurations` attribute names must equal each machine's `networking.hostName` — that's what makes bare `nixos-rebuild switch --flake .` work on-machine.
- `stateVersion` (system and home) is set once at first install; never bump it.
- The repo checkout lives at `~/nix-config` on every machine. `home/neovim.nix`'s out-of-store symlink hardcodes that path, and its failure mode is silent (a dangling `~/.config/nvim` — nvim just runs configless). Any future out-of-store symlink must use the same base path. `modules/nix-config.nix` auto-clones the checkout on the first boot that has network (ConditionPathExists on `~/nix-config/.git` — the *marker file*, not the bare directory: a home-manager activation script used to seed the directory before the network was up, and although that script is gone the marker stays correct whatever else ever pre-seeds the directory — makes it a permanent no-op once a real checkout exists; the clone itself is init+fetch+checkout so it tolerates a non-empty directory), so a fresh nixos-anywhere install self-heals instead of booting with every symlink dangling.
- The session lifecycle is systemd-NATIVE now, with exactly one custom pair to keep intact: `home/niri.nix` declares `niri-session.target` (BindsTo graphical-session.target, deliberately **no Install section** — it must only ever be reached explicitly, which is what scopes dms.service to THIS session), and `home/niri/config.kdl`'s `spawn-at-startup "systemctl" "--user" "start" "niri-session.target"` is the explicit start. Keep them paired. niri runs startup spawns only AFTER importing WAYLAND_DISPLAY into the user manager (Type=notify readiness), so everything the target pulls up sees the display — the env/startup race hyprland needed a one-command `sh -c '… && …'` dance for is solved upstream, and teardown needs no hook at all (niri.service BindsTo graphical-session.target). Don't convert the spawn into a `Wants=` on niri.service: that would queue the target at service START, racing the env import.
- Boot loader settings live in `core.nix`, *not* hardware-configuration.nix, so regenerating the hardware file can't drop them.
- home-manager's release branch must match the nixpkgs release when bumping either.

## Deliberate decisions (do not "fix")

Choices that look like gaps but are intentional. Don't "improve" them unprompted:

- **Editor configs stay plain files.** Neovim configs are ordinary config files symlinked via home-manager — never convert them to nixvim or other Nix-generated equivalents.
- **No Mason, ever.** LSPs and formatters are declared as Nix packages in `home/`, not installed by the editor.
- **DMS is the one shell — no second bar/launcher/locker/notification daemon** (no waybar, fuzzel, swaync, gtklock, swayidle, kanshi, other frameworks), **no extra compositors** — unless the human explicitly asks. Two notification daemons or two polkit agents on one bus is breakage, not choice.
- **DMS settings are GUI-owned on purpose.** Everything lives in `~/.config/DankMaterialShell/settings.json`, written by the Settings GUI — machine-local, never tracked, never "drift" to be reverted. Don't manage it from Nix (the home module's `settings` option makes the GUI fight Nix — the first DMS era already rejected it), and accept the cost: the curated baseline noctalia's tracked config.toml carried (idle timeouts, theme toggles) is a per-machine first-login GUI pass now, documented in the shell section above.
- **`home/niri/config.kdl` tracks STOCK niri defaults on purpose** — the human is learning niri's own keymap and workspace model this round (the opposite of the hand-tuned hyprland era). Every departure from stock is marked `// DEVIATION` and limited to: the DMS shell binds (launcher/lock/panels/audio/brightness via `dms ipc call`, screenshots via `screenshot-annotate`), Ctrl+Space us↔th (`switch-layout`, with NO xkb `grp:` option — both at once double-switch and cancel out), the session spawn-at-startup, prefer-no-csd, natural-scroll everywhere, and the includes. Don't add convenience binds, don't re-create hyprland-era binds (no window-switcher binds — niri's Mod+O overview covers it), don't emulate static workspace pins with named workspaces, and don't resurrect the pre-niri scratchpads or melange palette. Monitors are the one thing that never goes in the shared file: they live per machine in `home/niri/hosts/<hostname>.kdl` (tracked, hand-maintained, selected by Nix — see the desktop-split section above), copied from the machine, never invented. Don't push the split back into the KDL by reading `/etc/hostname`, and don't generate the output blocks from Nix — these stay plain files so a layout tweak is one edit, applied on save.
- **HDR is parked, not forgotten.** niri 26.04 has no color management ("we don't support HDR or color management yet"), so gaming.nix and mpv.nix carry short SDR-only notes instead of the hyprland-era auto-HDR config (recipe preserved in git history). Don't try to re-add HDR plumbing until niri ships it.

## Style

Files are heavily commented in a teaching style — comments explain *why* a setting exists and what would break without it. Match that density and tone when editing.
