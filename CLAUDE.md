# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A NixOS flake for two x86_64-linux machines: `unclebeam-pc` (AMD Ryzen 9 desktop + AMD RDNA GPU, gaming) and `unclebeam-thinkpad` (ThinkPad X1 Carbon Aura, Intel). Both run NixOS 26.05 + Hyprland 0.55+ with its **Lua config** (the compositor lineage is sway → hyprland → niri → hyprland again: this branch re-trials hyprland as a FULL replacement after it lost the first side-by-side trial and was deleted 2026-07-11; the niri setup lives in git history on `main`). The repo is edited primarily **on the Linux machines themselves**; the Mac is used as a remote install trigger (nixos-anywhere) and can only `nix eval` for validation — it can never build or switch.

## Commands

```sh
# Validate a config after edits (works cross-platform, incl. this Mac —
# evaluation only, no build). This is the main "did I break it" check:
nix eval .#nixosConfigurations.unclebeam-pc.config.system.build.toplevel.drvPath
nix eval .#nixosConfigurations.unclebeam-thinkpad.config.system.build.toplevel.drvPath

# Apply on a machine (hostname == flake attr, so no #name needed there):
sudo nixos-rebuild switch --flake .

# Smoke-test in a VM (Linux only):
nixos-rebuild build-vm --flake .#unclebeam-pc && ./result/bin/run-unclebeam-pc-vm

# Update pins (stays within the nixos-26.05 branch):
nix flake update
```

**⚠ Flakes only see git-tracked files.** After creating any new `.nix` file, `git add` it before evaluating/building — otherwise you get misleading "path does not exist" errors.

## Hard-won rules

These each caused a real failure at least once. Follow them literally.

- **A change is not "done" until it evals, is committed, AND is pushed — but a manual gate splits the work.** Half-committed or unvalidated work broke an install once — the machine pulled a state where only part of a change existed. So the work happens in two stages with the human's own rebuild in between. First: `nix eval` passes for BOTH hosts, then `git add .`, and **stop there — do not commit or push yet.** The human rebuilds and switches on their own machine first; only once they confirm it works do you commit, push, and print the commit sha. When wiring a new flake input, verify all three places it must appear: the input declared in `flake.nix`, its module wired into `mkHost`, and the import in the host that uses it.
- **Never invent hardware facts.** `hardware-configuration.nix` contents, `/dev/disk/by-id/` paths, filesystem UUIDs — these only come from the target machine. If one is missing, stop and ask the human; leave a clearly marked placeholder rather than guessing. A plausible-looking made-up value is worse than a loud gap, because disko will happily format the wrong disk.
- **Installs and reinstalls must pin an exact commit sha** — `github:unclebeam/nix-config/<sha>#<host>` — to bypass Nix's flake tarball caching (a branch ref can serve a cached tarball up to an hour stale, i.e. *not* the commit you just pushed). Branch refs are fine only for daily on-machine rebuilds with `--flake .`, where the repo is a local checkout and there's nothing to cache.
- **Know which PAM service a display manager actually traverses.** When SDDM was the greeter, its PAM service was generated with `useDefaultRules = false` — a bare `substack login` — so per-service toggles like `sddm.kwallet`/`sddm.fprintAuth` were silent no-ops (one sat in niri.nix for months doing nothing; the keyring unlock actually came from a module hooking `login`). The current greeter runs on **greetd**, whose PAM service is generated WITH default rules and does NOT substack `login`: toggles on `security.pam.services.greetd` genuinely work, and toggles on `login` no longer fire at graphical login. (The Noctalia lock screen authenticates against `/etc/pam.d/login`, so that service still matters.) Before setting any per-service PAM option, check how that service is generated.
- **Every session entry the greeter lists must actually boot.** The hyprland package unconditionally ships a second session file, `hyprland-uwsm.desktop`; with `withUWSM` off, uwsm's systemd user units don't exist, and landing on that entry killed logins in under a second (journal 2026-07-20: uwsm ran `systemctl --user start wayland-session-bindpid@….service` → exit status 5 → session closed → bounced back to the greeter — the "login bounces on first attempt" bug). `modules/hyprland.nix` force-filters `services.displayManager.sessionPackages` down to the plain `hyprland.desktop` via a link-farm (never `overrideAttrs` — that rebuilds hyprland from source). If another compositor/session ever appears, extend that filtered list; don't remove the filter.

## Architecture

`flake.nix` defines a `mkHost` helper; each host is one `nixosConfigurations` entry whose modules are: the host dir, disko's NixOS module, and home-manager wired in as a NixOS module (`useGlobalPkgs`, so one `nixos-rebuild switch` builds system + user config together, and `allowUnfree` from core.nix applies to user packages too).

Three layers, each with a strict role:

- **`hosts/<name>/`** — deliberately THIN: hostname, hardware quirks (GPU, microcode, zram), `stateVersion`, and which shared modules to import. Importing a module *is* enabling it (e.g. the thinkpad gets gaming.nix by uncommenting one import line). Each host also has:
  - `hardware-configuration.nix` — machine-generated by `nixos-generate-config`; its `fileSystems.*` entries were removed because disko generates them.
  - `disko.nix` — declarative disk layout (GPT → 512M vfat ESP → btrfs with `@`/`@home` subvolumes, zstd compression). Dual purpose: nixos-anywhere uses it to **wipe and format** the disk at install time, and at run time it generates the mount config. Target disks are pinned by stable `/dev/disk/by-id/nvme-<model>_<serial>` paths, never `/dev/nvme0n1`.
- **`modules/`** — shared NixOS (system-level) modules: `core.nix` (nix settings, systemd-boot, NetworkManager, the user, baseline packages), `nix-config.nix` (first-boot clone of the `~/nix-config` checkout — the target of every out-of-store symlink; no-op once it exists), `desktop.nix` (fonts + Wayland-wide env + fallback GTK portal), `hyprland.nix` (hyprland session + portal routing: KDE for dialogs, hyprland for capture), `noctalia.nix` (THE Noctalia shell: flake NixOS module enable + noctalia.service + cachix substituter + UI fonts), `noctalia-greeter.nix` (login greeter: Noctalia's greeter UI on greetd), `kwallet.nix` (session keyring: ksecretd + pam_kwallet auto-unlock on `greetd`; user half in `home/kwallet.nix`), `dolphin.nix` (avahi, udisks2, ntfs/exfat — the system half of the file manager), `audio.nix`, `gaming.nix`, `laptop.nix`.
- **`home/`** — shared home-manager (user-level) config, identical on both machines; entrypoint `home/default.nix` imports hyprland/noctalia/alacritty/fish.

**System vs. user split for the desktop**: `modules/hyprland.nix` enables hyprland at the system level (session .desktop file, portals, XWayland); the actual window-manager *configuration* lives in `home/hyprland.nix` plus the plain Lua files `home/hypr/hyprland.lua` and `home/hypr/binds.lua` (**out-of-store** symlinked into the `~/nix-config` checkout — same rule and same hardcoded base path as the editor configs, so edits apply on a bare `hyprctl reload` with no rebuild. hyprland 0.55+ loads hyprland.lua INSTEAD of hyprland.conf, and does not watch it — `hyprctl reload` after editing). Machine-local monitor config lives in `home/hypr/local/outputs.lua` — gitignored, hand-maintained `hl.monitor()` lines, seeded empty by `home/hyprland.nix`'s activation script (monitors are hardware facts that must never sync between hosts, and Lua's `require()` hard-fails on a missing file). Keep additions on the right side of that line: config-less system packages go in core.nix, apps with per-user config go in home/.

**One file per intent**: everything that exists *because of* one app lives in that app's file. If Dolphin needs a system service, the app goes in `home/dolphin.nix` and the service in `modules/dolphin.nix` — not a generic file. Removing an app must be atomic: delete one file plus its import line, leaving zero orphaned config behind. Only promote settings to a shared file when a second consumer actually appears, never preemptively.

**The shell is Noctalia v5; apps are KDE; screen capture is the hyprland portal.** Since 2026-07 (replacing DMS, which had replaced waybar/fuzzel/swaync/gtklock/swayidle/plasma-polkit-agent/power.nix/SDDM), one native process (the `noctalia` flake input) is the bar, launcher, notification daemon, lock screen, idle policy, OSD, clipboard history, polkit agent, power menu, wallpaper, screenshot tool — and its sibling flake `noctalia-greeter` is the greetd greeter. **v5 is a ground-up C++ rewrite: nixpkgs' `noctalia-shell` package is the old v4 Quickshell app — never substitute it for the flake input.** The flake inputs deliberately have NO `inputs.nixpkgs.follows` (unlike every other input): noctalia.cachix.org only caches upstream's-pin builds, and following our nixpkgs would silently recompile the C++ shell from source on every machine (substituter + key live in `modules/noctalia.nix`; if a rebuild visibly compiles noctalia, that wiring regressed). Upstream ships a NixOS module AND a home-manager module — we use the **NixOS module only** (`modules/noctalia.nix`: enable + the one `noctalia.service` user unit scoped to hyprland-session.target + cachix + upower/ppd + UI fonts; `modules/noctalia-greeter.nix`: greeter, which enables greetd itself; `home/noctalia.nix`: user-side glue ONLY — adw-gtk3 + the out-of-store `~/.config/noctalia` symlink + template-output placeholders, it imports no noctalia module). Never re-import the flake's homeModule (two service owners), and never spawn `noctalia` from hyprland.lua — the shell must not run twice. Interaction is `noctalia msg …` (`noctalia msg --help` lists all); **the keybinds are OURS**, hand-written in the tracked `home/hypr/binds.lua` (Noctalia manages no compositor config — no fragments, no setup command; DMS's generated-binds era is over). Configuration is LAYERED, and this is the load-bearing difference from DMS: defaults → our tracked `home/noctalia/config.toml` (out-of-store symlink, hot-reloaded via inotify on every save — no rebuild, no reload command) → the GUI's own `~/.local/state/noctalia/settings.toml`, which loads last and wins. So the repo TOML declares the curated must-haves (polkit_agent on, screenshot→satty pipe, idle/lock timeouts, theme templates) while the Settings GUI (SUPER+comma) stays fully usable — GUI tweaks are machine-local overrides; promote one into config.toml when it should hold on both machines. A fresh install therefore boots to a WORKING desktop with NO shell-side manual step — once it has network: modules/nix-config.nix clones the checkout (retrying every 15s until network/DNS actually works — a first boot without it bounced logins on a dangling hyprland.lua until the 2026-07-21 retry hardening; login is only possible ≤15s after network comes up), the tracked binds.lua + config.toml provide keybinds and policy, and the greeter lists exactly one session. First-login steps that remain: pick a wallpaper (SUPER+Y) so the palette + templates have a source image, and (thinkpad) `fprintd-enroll`. Doom Emacs keeps its own split (`home/emacs.nix`): the framework clone into `~/.config/emacs` is automatic (the `clone-doom-emacs` user oneshot, ConditionPathExists-guarded like the nix-config clone; retries next login if network wasn't up), while `doom install` — minutes of package building, upstream's interactive path — is a manual first-login step, followed by `systemctl --user restart emacs.service` so the daemon (which started bare) loads Doom. The KDE app layer stays: Dolphin + Ark + KIO, secrets in ksecretd (`modules/kwallet.nix` + `home/kwallet.nix`, auto-unlocked via pam_kwallet on `greetd` — which is why the greeter must stay password-only, see modules/fprintd.nix), dialogs/notifications/settings route to `xdg-desktop-portal-kde`. Do not re-add gnome-keyring. The exception: ScreenCast/Screenshot/GlobalShortcuts route to `xdg-desktop-portal-hyprland` (hyprland's native wlr-screencopy backend; RemoteDesktop is pinned to `none` — xdph doesn't implement it). Never route the capture family to `kde` — xdg-desktop-portal-kde's capture code is hard-wired to KWin's private `zkde_screencast` protocol and can never work here. (Screenshots themselves don't go through the portal: `noctalia msg screenshot-region/-fullscreen` capture natively and `[shell.screenshot]` pipes the PNG into satty — `home/satty.nix` owns the annotator, the pipe config lives in config.toml.)

**Theming**: Noctalia owns color. The shell derives a Material You palette from the wallpaper (`[theme] source = "wallpaper"`) and its **built-in template engine** (re)renders, per the opt-in `builtin_ids` list in `home/noctalia/config.toml`: `~/.config/hypr/noctalia.lua` (border colors — loaded by a *guarded* require in hyprland.lua whose literal `require("noctalia")` string doubles as the marker the template's apply.sh greps for, and applied via the `colors_changed = "hyprctl reload"` hook since hyprland doesn't watch files), `~/.config/alacritty/themes/noctalia.toml` (imported by alacritty.nix — importing that exact path is also what keeps apply.sh from trying to edit our read-only store-symlinked alacritty.toml), `~/.config/gtk-{3,4}.0/noctalia.css` (apply.sh @imports it into gtk.css, sets adw-gtk3(-dark) + the org.gnome color-scheme; gtk4's is also @imported by `home/hypr/share-picker.css`), and `~/.local/share/color-schemes/noctalia.colors` (a KColorScheme, merged into `~/.config/kdeglobals` for live KF6 recolor; `home/qt.nix` also points qt6ct/qt5ct's `color_scheme_path` at it and sets `QT_QPA_PLATFORMTHEME=qt6ct` — Dolphin needs the KDE build, `kdePackages.qt6ct`). All template outputs are written imperatively by noctalia — configs reference them via includes/imports, never via a store symlink (that would block the writes). They're machine-local and untracked (each machine's wallpaper differs); `home/noctalia.nix`'s activation script seeds the alacritty and hypr outputs as empty placeholders so nothing dangles before the first render. Add a template id only together with its consumer. There is no repo palette; don't hardcode theme colors in app configs — let the templates reach them, or leave the app at its defaults (satty, mangohud).

**Invariants to preserve**:
- `nixosConfigurations` attribute names must equal each machine's `networking.hostName` — that's what makes bare `nixos-rebuild switch --flake .` work on-machine.
- `stateVersion` (system and home) is set once at first install; never bump it.
- The repo checkout lives at `~/nix-config` on every machine. `home/neovim.nix`'s out-of-store symlink hardcodes that path, and its failure mode is silent (a dangling `~/.config/nvim` — nvim just runs configless). Any future out-of-store symlink must use the same base path. `modules/nix-config.nix` auto-clones the checkout on the first boot that has network (ConditionPathExists on `~/nix-config/.git` — the *marker file*, not the bare directory, because home-manager's activation seeds `~/nix-config/home/hypr/local/` before the network is up — makes it a permanent no-op once a real checkout exists; the clone itself is init+fetch+checkout so it tolerates that pre-seeded directory), so a fresh nixos-anywhere install self-heals instead of booting with every symlink dangling.
- The session lifecycle is symmetric, and both halves live in `home/hypr/hyprland.lua`: the startup hook pushes the env and starts `hyprland-session.target` as ONE `sh -c '… && …'` command (two separate spawns raced — the shell service could start without `WAYLAND_DISPLAY`), and a `hyprland.shutdown` hook stops `graphical-session.target` on compositor exit (without it, logout left the user manager holding the dead session's env and the next login's shell came up broken). Don't remove either half, and keep them paired.
- Boot loader settings live in `core.nix`, *not* hardware-configuration.nix, so regenerating the hardware file can't drop them.
- home-manager's release branch must match the nixpkgs release when bumping either.

## Deliberate decisions (do not "fix")

Choices that look like gaps but are intentional. Don't "improve" them unprompted:

- **Editor configs stay plain files.** Neovim configs are ordinary config files symlinked via home-manager — never convert them to nixvim or other Nix-generated equivalents.
- **No Mason, ever.** LSPs and formatters are declared as Nix packages in `home/`, not installed by the editor.
- **Noctalia is the one shell — no second bar/launcher/locker/notification daemon** (no waybar, fuzzel, swaync, gtklock, swayidle, kanshi, other frameworks), **no extra compositors** — unless the human explicitly asks. Two notification daemons or two polkit agents on one bus is breakage, not choice.
- **Noctalia config is layered on purpose: tracked TOML for the baseline, GUI for the rest.** `home/noctalia/config.toml` (hot-reloaded, out-of-store) holds only the must-haves that make a fresh install work on both machines; the Settings GUI writes its own `~/.local/state/noctalia/settings.toml`, which loads last and wins — GUI overrides are legitimate and machine-local, never "drift" to be reverted. Don't move the whole config into Nix (the home module's `settings` option), and don't strip config.toml to force everything through the GUI.
- **`home/hypr/hyprland.lua` and `home/hypr/binds.lua` are fully OURS** — Noctalia writes no compositor config, so there is no upstream template to track (that was the DMS era). Monitors are the one thing that never goes in the shared files: they live in the gitignored, hand-maintained `home/hypr/local/outputs.lua` per machine, and per the hardware-facts rule they are copied from the machine, never invented. Never resurrect the pre-niri personalized hyprland config's scratchpads or melange palette. (Custom animations and the group-toggle bind ARE back by choice — this rule used to ban them too, but the current files have them deliberately.)

## Style

Files are heavily commented in a teaching style — comments explain *why* a setting exists and what would break without it. Match that density and tone when editing.
